# 要件定義書

## はじめに

本ドキュメントは、暗号通貨取引アプリケーションのTradeページに「Current Orders」コンポーネントを実装するための要件を定義します。このコンポーネントは、未約定の売買注文を自動更新機能付きで表示し、ユーザーに保留中の注文のリアルタイム表示を提供します。

## 用語集

- **システム**: Current Ordersコンポーネントと関連機能
- **Current Orders**: システム内でまだアクティブな未約定の売買注文
- **未約定注文**: 発注されたが、まだ実行またはキャンセルされていない注文
- **自動更新**: ユーザーの操作なしに定期的にデータを自動更新すること
- **注文詳細**: 日付、価格、数量を含む注文に関する情報
- **買い注文**: 暗号通貨の購入注文
- **売り注文**: 暗号通貨の売却注文
- **Bitflyer Lightning API**: Bitflyerが提供する取引所APIサービス
- **Child Orders**: Bitflyer APIにおける個別の注文（未約定注文を含む）

## 要件

### 要件1

**ユーザーストーリー:** トレーダーとして、Tradeページで現在の未約定注文を確認したい。そうすることで、別のページに移動することなく保留中の取引を監視できる。

#### 受入基準

1. Tradeページが読み込まれたとき、システムはOrder Detailsセクションの下に「Current Orders」コンポーネントを表示しなければならない
2. 現在の注文が表示されるとき、システムは買い注文と売り注文を別々のセクションで表示しなければならない
3. 注文が表示されるとき、システムは各セクション（買い/売り）で最大10件の注文を表示しなければならない
4. 注文が表示されるとき、システムは日付の降順（最新順）でソートしなければならない
5. 注文が存在しないとき、システムは適切な空の状態メッセージを表示しなければならない

### 要件2

**ユーザーストーリー:** トレーダーとして、各注文の詳細情報を確認したい。そうすることで、保留中の取引のステータスと詳細を理解できる。

#### 受入基準

1. 注文が表示されるとき、システムは注文日時をYYYY/MM/DD HH:MM:SS形式で表示しなければならない
2. 注文が表示されるとき、システムは注文価格を適切なフォーマットでJPYで表示しなければならない
3. 注文が表示されるとき、システムは注文数量を暗号通貨単位で表示しなければならない
4. 注文が表示されるとき、システムはすべての数値に一貫したフォーマットを使用しなければならない
5. 注文が表示されるとき、システムは買い注文と売り注文を視覚的に明確に区別しなければならない

### 要件3

**ユーザーストーリー:** トレーダーとして、現在の注文が自動的に更新されることを望む。そうすることで、手動でページを更新することなくリアルタイムの変更を確認できる。

#### 受入基準

1. Current Ordersコンポーネントがマウントされたとき、システムは10秒ごとに自動更新を開始しなければならない
2. コンポーネントがアンマウントされたとき、システムはメモリリークを防ぐために自動更新を停止しなければならない
3. 自動更新が発生するとき、システムはバックエンドAPIから更新された注文データを取得しなければならない
4. 自動更新が失敗したとき、システムはUIを壊すことなく適切にエラーを処理しなければならない
5. 新しいデータが受信されたとき、システムはユーザーの操作を妨げることなく表示を更新しなければならない

### 要件4

**ユーザーストーリー:** トレーダーとして、現在の注文コンポーネントが既存のTradeページとシームレスに統合されることを望む。そうすることで、ユーザーエクスペリエンスが一貫性があり直感的に保たれる。

#### 受入基準

1. コンポーネントがTradeページに追加されるとき、システムはOrder Formコンポーネントの下に配置しなければならない
2. コンポーネントが表示されるとき、システムは他のページコンポーネントと同じスタイリングと色スキームを使用しなければならない
3. コンポーネントが表示されるとき、システムはモバイルデバイス向けのレスポンシブデザインを維持しなければならない
4. コンポーネントが表示されるとき、システムは既存のデザインパターンと間隔に従わなければならない
5. コンポーネントが読み込まれるとき、システムは既存のページ機能に干渉してはならない

### 要件5

**ユーザーストーリー:** 開発者として、BitflyerのAPIから現在の注文を取得するバックエンドAPIエンドポイントが欲しい。そうすることで、フロントエンドがリアルタイムの注文情報を表示できる。

#### 受入基準

1. APIエンドポイントが呼び出されたとき、システムはBitflyer Lightning APIから未約定注文を取得しなければならない
2. Bitflyer APIから注文データを取得するとき、システムはGET /v1/me/getchildorders エンドポイントを使用しなければならない
3. 注文が返されるとき、システムは注文ID、タイプ（買い/売り）、ペア、価格、数量、作成日時を含めなければならない
4. 注文が返されるとき、システムは結果をタイプ（買い/売り）ごとに10件に制限しなければならない
5. 注文が返されるとき、システムは作成日時の降順でソートしなければならない
6. Bitflyer APIが利用できないとき、システムは適切なエラーメッセージを返さなければならない

### 要件6

**ユーザーストーリー:** 開発者として、現在の注文機能に適切なエラーハンドリングが欲しい。そうすることで、失敗がユーザーエクスペリエンスを壊さない。

#### 受入基準

1. APIリクエストが失敗したとき、システムはユーザーにエラーメッセージを表示しなければならない
2. ネットワーク接続が失われたとき、システムは指数バックオフでリクエストを再試行しなければならない
3. APIが無効なデータを返したとき、システムは適切に処理してフォールバックメッセージを表示しなければならない
4. エラーが発生したとき、システムはデバッグ用に適切なエラー情報をログに記録しなければならない
5. エラーが解決されたとき、システムは自動的に通常の動作を再開しなければならない

### 要件7

**ユーザーストーリー:** トレーダーとして、現在の注文コンポーネントがパフォーマンス良く動作することを望む。そうすることで、Tradeページが遅くなったり、過度なリソースを消費したりしない。

#### 受入基準

1. 自動更新がアクティブなとき、システムはコンポーネントが表示されているときのみAPIコールを行わなければならない
2. ユーザーがタブを切り替えたりブラウザを最小化したりしたとき、システムは自動更新を一時停止しなければならない
3. ユーザーがページに戻ったとき、システムは即座に自動更新を再開しなければならない
4. 注文をレンダリングするとき、システムはUIの遅延を防ぐために効率的なレンダリング技術を使用しなければならない
5. 複数の注文が表示されるとき、システムはスムーズなスクロールと操作を維持しなければならない
